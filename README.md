# Zach's Personal Site

## Testing

```
# Backend unit and API tests
cd graphql-server && ./gradlew test

# Frontend component tests
cd frontend && npm test

# End-to-end tests: starts the backend and a production build of the frontend
cd e2e && npm install && npx playwright install chromium && npm test
```

The Vulkan Retro PPU's page (`/projects/vkPPU`) runs its games in the browser on WebGPU. They are built from the [vk_ppu](https://github.com/zach-youssef/vk_ppu) submodule (`external/vk_ppu`, with its own `vulkan_test` submodule) by `./build-ppu` into `graphql-server/assets/ppu`, which git ignores and the backend serves as `/assets/ppu/<game>/`. Run it before the end-to-end tests or a local backend, and again after updating the submodule; `./bundle` (and so `./deploy`) runs it itself. Building needs what the PPU's `make web` needs: Racket 8 and Node 24 with npm.

ZGAL's page (`/projects/zgal`) likewise runs one of its examples beside the program's source, chosen with a selector that records it in the URL (`?sample=particles` or `?sample=scene`; a missing or unknown value shows particles), so a link can open the page on either; choosing the running example again restarts it (scene stops on Esc). The examples are listed in `frontend/src/features/zgal/samples.ts`. `./build-zgal` builds ZGAL's examples that run in a browser (particles and scene) from the [vulkan_testing](https://github.com/zach-youssef/vulkan_testing) submodule (`external/zgal`) into `graphql-server/assets/zgal`, each served as `/assets/zgal/<name>/`: its page and scripts, the runtime, whatever it loads (scene's `assets/scene.gltf` and `scene.bin`, and any `*.wasm`), its source (`<name>.zgal`, which the backend serves as UTF-8 text so that a browser shows it) and a screenshot for browsers without WebGPU. Each screenshot is the last frame of a headless run under Node on the GPU (particles at 1024x640, scene at 1280x720, 240 frames each), compressed with `cwebp` (`brew install webp`); a program is added with one `copy_program` line in `./build-zgal`. It also builds ZGAL's Scribble documentation into `graphql-server/assets/zgal/docs`, which the backend serves at `/zgal/docs/` (and redirects `/zgal/docs` there, since the page links its stylesheets relative to itself); the ZGAL page links to it. Last, it writes `graphql-server/assets/zgal/source.json`, served as `/assets/zgal/source.json`, which says where the copied sources come from: `{"repository": "https://github.com/zach-youssef/vulkan_testing", "commit": <the checkout's HEAD>, "dirty": <bool>}`. `dirty` is true when GitHub may not have those sources at that commit: when the checkout has changes (untracked files included), isn't the `external/zgal` submodule, isn't at the commit the site pins it to, or is at a commit none of its remote branches has (unpushed, or not fetched since). The page loads it once and links each listing to its source on GitHub at that commit (`<repository>/blob/<commit>/examples/<name>/<name>.zgal`, labelled with the short sha), or says "local build" instead when `dirty` is true. The listing always shows the copied file, so the page fetches nothing from GitHub, and it still shows, without the link, when `source.json` can't be loaded. The checkout must be a git repository of its own; `./build-zgal` refuses anything else before building. The end-to-end tests (`zgalSource.spec.ts`) check that each served `<name>.zgal` is the one at the submodule's pinned commit, that `commit` is that commit and that `dirty` is false, and that the page lists each program exactly as it is at that commit and links it to GitHub at that commit, so a build from a changed or other checkout fails them. Both pages run their programs in frames of the programs' own pages (`ZgalFrame.tsx`); `ZgalCanvas.tsx` runs one in a canvas of the site's page instead, importing its main (`<name>.zgal.main.js`) at run time and calling its `mount` (ZGAL's "Other pages embed programs"). It stops the program on unmount and mounts it again when its main, scaling or command line changes. Every mount, in whichever `ZgalCanvas`, first waits until the programs stopped before it have stopped, as each has its own WebGPU device and copy of its assets, so a canvas re-keyed or reached again by navigating back doesn't hold a second copy of a scene. The wait is capped at 10 s (`STOP_WAIT_MS`), because a stop can hang on a stalled asset download; past the cap the mount logs a console warning and goes ahead, so a second copy is possible only after a stop has hung. Its `onState` and its box's `data-zgal` attribute give the state (`loading` as each mount starts, then `running`, `stopped` or `failed`). The dev and preview servers forward `/assets/zgal` to the backend, so such an import works in both.

The splat viewer (vk_splats' `splat_view`, which draws a 3D Gaussian splatting scene as it streams in) runs on WebGPU too, with a scene trained by [vk_splats](https://github.com/zach-youssef/vk_splats). `./build-splat` builds the viewer from the vk_splats submodule (`external/vk_splats`, with its own `vulkan_test` submodule) into `graphql-server/assets/splat`, which git ignores and the backend serves as `/assets/splat/`: the viewer's page, scripts and runtime in `viewer/` (a page imports `viewer/splat_view.zgal.main.js` and mounts it), the scene in `scene/` (`scene.stream` and its `cameras.bin`), `screenshot.webp` for browsers without WebGPU, and `scene.json`, which tells a page what it needs so that it hard-codes none of it: the viewer's main, the screenshot, the scene's files with their paths, sizes and sha256s, their total `bytes` (a progress bar's total, whatever the response's headers say), the splat count, SH degree and stream format version, the viewer's `size`, its command line (`args`, with root-absolute paths, which ZGAL's `mount` resolves against the page's origin), the release (`tag` and `url`) and `source`, the viewer's repository and commit with a `dirty` flag decided as `./build-zgal` decides it for its `source.json`. The scene isn't in git: it is a release's assets on vk_splats, which the tracked lock `splat-scene.json` names with their sizes and sha256s, along with the stream format version, the splat count and SH degree, and the view the page opens on (`camera` of `cameras.bin`, the canvas `size`, and `streamWords`, the 4-byte words the viewer reads a frame: 262,144, 1 MiB, given explicitly as splat_view's default is 4 MiB). `./build-splat` downloads each locked file once into `${SPLAT_CACHE_DIR}/<sha256>` (by default `${XDG_CACHE_HOME:-~/.cache}/personal-site/splat`), checks its size and sha256 before it enters the cache and every time after, and refuses a stream whose header (magic, format version, splats, SH degree) isn't the lock's, or a vk_splats checkout whose stream format version (`lib/splat_stream.zgal`) isn't the lock's, since a viewer refuses a stream of another version. It also puts the lock's fixture, a 2,000-splat stream and its cameras for the end-to-end tests, in `e2e/fixtures/splat/` (ignored by git, not shipped). The screenshot is the last frame of a headless run under Node on the GPU with the page's command line, at the lock's camera and size, but for `--stream-words`, which is splat_view's most so that a slow GPU (lavapipe in CI) loads the scene in fewer, longer frames; the run must report the whole scene loaded: it runs 32 frames, enough on lavapipe (which has the scene in 3, as Node reads the file at its own pace, and spends about 0.3 s on every frame after), and again with 480 if that wasn't enough (an M4 takes about 280); then `cwebp` compresses it (quality 80). Building needs what vk_splats' web build needs (Racket 8 and Node 24 with npm), `jq` and `curl`. The splat page (`/projects/splats`, `frontend/src/features/splat/`) loads `scene.json` and mounts the viewer in a `ZgalCanvas` with its `args`: as the page opens on a desktop, but on a touch device (a coarse primary pointer) only once the visitor presses "View in 3D (N MB)" over the screenshot, so a phone downloads the scene only when asked. A progress bar in the theme's primary colour counts the bytes the viewer's `onProgress` reports against `scene.json`'s `bytes`, from the first report until every byte has arrived (a viewer built without `onProgress` shows none). Without WebGPU, or when the viewer fails, the page shows the screenshot with an alert; once Esc has stopped the viewer, a button restarts it. The dev and preview servers forward `/assets/splat` to the backend, as they do `/assets/zgal`.

To swap the scene: publish the new scene as a new release on vk_splats (a new tag rather than new assets on the old one, so older commits' locks still download what they name), then in one commit update `splat-scene.json` (the tag, each file's bytes and sha256, the splat count, SH degree, stream format version and the start view) and, if the scene needs a newer viewer (a new stream format version, say), bump `external/vk_splats` with it. `./build-splat` refuses a lock whose version the pinned viewer doesn't read, so the two can't drift apart.

```
git submodule update --init --recursive
./build-ppu                 # or ./build-ppu <another ppu checkout>
./build-zgal                # or ./build-zgal <another zgal checkout>
./build-splat               # or ./build-splat <another vk_splats checkout>
```

The frontend requests the backend relative to the page, since the backend serves the site in production. The Vite dev and preview servers forward those requests to the backend at `BACKEND_URL`, which defaults to `http://localhost:8080`, the port the backend listens on when run locally:

```
# Local backend and frontend dev server, in separate terminals
cd graphql-server && ./gradlew run
cd frontend && npm start

# Frontend dev server against the live backend
cd frontend && BACKEND_URL=http://zyoussef.com npm start
```

The end-to-end tests point the preview server at the test backend, so they never touch the live site.

## CI

GitHub Actions (`.github/workflows/ci.yml`) builds and tests every commit a push brings, each in its own job on `ubuntu-24.04`: on `master` the commits the push added, on any other branch every commit that `master` doesn't have; in either case the newest 20 at most. A newer push to a working branch cancels the checks still running for its older one, while every push to `master` is checked in full. Each job runs `tests/deploy-test.sh` (with its lock tests, as the runner has `flock`), the frontend tests, `./build-ppu`, `./build-zgal`, `./build-splat`, the backend tests and the end-to-end tests, and its commit gets a `CI / test` commit status, so a branch shows which of its commits pass.

- The public submodules are checked out over https. SeamCarving is private, so it's checked out with a read-only deploy key on [SeamCarving](https://github.com/zach-youssef/SeamCarving), whose private half is the repository secret `SEAMCARVING_DEPLOY_KEY`.
- Without a GPU, `./build-zgal` and `./build-splat` draw their screenshots on Mesa's software Vulkan driver (lavapipe), so they can differ from those drawn on a Mac. Each job uploads them as the `screenshots-<sha>` artifact (`zgal/<name>/screenshot.webp` and `splat/screenshot.webp`).
- `./build-splat`'s downloads of the locked scene are cached (`actions/cache` on `~/.cache/personal-site/splat`, which setup-build hands `./build-splat` as `SPLAT_CACHE_DIR`) under a key made of the sha256s in `splat-scene.json`, so a job downloads the scene only when the lock names a new one; `./build-splat` checks every cached file against the lock anyway.
- The WebGPU specs run Chromium's WebGPU on SwiftShader rather than a GPU, so CI and a Mac run them the same way (see `e2e/tests/webgpu.ts`).
- Tests print a dot each and their failures in full when `CI` is set. On a failure, the job uploads the Playwright report with the failures' traces (`e2e-report-<sha>`) and the backend's test report (`backend-test-report-<sha>`); `gh run download <run id>` fetches them.

Notes for editing the workflow:

- The submodule checkouts, the splat scene's download cache and the toolchains (Racket, Node, Java, Gradle, lavapipe, cwebp) are set up by the local action `.github/actions/setup-build`, which every job that builds the site uses. A job must check out the repository before it can use it. The test jobs run the steps of the pushed tip's `ci.yml`, but each uses the setup-build of the commit it checks out, so a commit that a new step needs set up must set it up itself (e.g. the vk_splats checkout comes with the submodule, before `./build-splat`'s CI step).
- `actionlint` (`brew install actionlint shellcheck`) checks the workflows and their scripts locally; its only expected findings are the unused `try` loop variables.
- Status functions (`cancelled()`, `failure()`) are only allowed in `if:`. In `env:` they make the whole workflow fail to parse, as a 0 s "workflow file issue" run with no message; use `job.status` there.
- `git -c url.<https>.insteadOf=<ssh> submodule update --recursive` passes the rewrite on to nested submodules (through `GIT_CONFIG_PARAMETERS`), so it needs no global rewrite, which would also send the private SeamCarving over https.
- `gradle/actions/setup-gradle` stays on v5, the last MIT major: v6 accepts the Terms of Use of a closed-source caching component.
- The SeamCarving checkout (in `setup-build`), which holds the deploy key, runs before any npm, Gradle or build step, so no third-party script runs before the key is used and removed.
- Only jobs that run no code from the commits, npm, Gradle or third-party actions hold a token that can post statuses, as a job's steps share one user and file system (a build could plant a `gh` that a later step runs with the token). The test jobs get `contents: read` and no `GH_TOKEN`, and no checkout persists its credentials. The `pending` job marks every commit pending; the `statuses` job, which needs those and the test jobs, posts each commit's status from the conclusion of its job (named `Test <sha>`) in the run's jobs API, linked to that job: anything but success or failure (cancelled, timed out, skipped or unreadable) is an `error`, so none stays pending. Neither of the two checks anything out.

## Deployment

Pushing to `master` deploys the site, once CI passes (see "Continuous deployment" below). `./deploy` does the same from a local checkout, as a manual fallback: it builds the site and deploys it to the server. It runs the two steps a deploy has, which can also run apart (e.g. building once and shipping the result later):

```
./bundle [--skip-tests] <out-dir>   # build into <out-dir>/site-bundle.zip, with a copy of its MANIFEST
./ship <bundle.zip>                 # deploy that bundle
```

`./bundle` builds the frontend, the PPU's games, ZGAL's examples, the splat viewer with its scene and the backend, and zips them with `server-restart`, `server-deploy` and `Caddyfile`, laid out as they go in the server's home directory. Of `graphql-server/assets` only the files git tracks ship, besides the PPU's, ZGAL's and the splat viewer's builds (`assets/splat`, about 26 MB, nearly all of it the scene's stream), so untracked local files don't. ZGAL's build includes `source.json`, and the splat viewer's `scene.json`, which record the commit their sources were copied from; check that both say `"dirty": false` before shipping a bundle built locally. The zip's `MANIFEST` lists every file in it.

`./ship` sends the zip over ssh to `server-deploy` on the server, on its stdin, as the only command it runs, so it also works with a deploy key limited to `restrict,command="~/server-deploy"` in `~/.ssh/authorized_keys`. `server-deploy` unpacks the zip into `~/.deploy/staging` and checks it before changing anything, so a broken upload leaves the site as it was. It then moves the files into place, deletes the files the previous deploy's manifest (kept in `~/.deploy/MANIFEST`) listed and this one doesn't, keeps the new manifest and runs `server-restart`. A file it can't delete is reported and the deploy carries on, failing at the end. Once the upload is in, a dropped ssh session doesn't stop it; `~/.deploy/log` holds the last deploy's messages. Deploys run one at a time under a lock taken with `flock`, which the server needs (util-linux). Renaming or removing a file needs nothing more than the change itself: the next deploy deletes the old one from the server. That includes a path changing between file and directory: an old deploy's file or directory in the way is deleted before the install, while anything else in the way refuses the bundle. `tests/deploy-test.sh` tests `server-deploy` against temporary directories.

The server also holds files that no deploy ships but that are still in use: `resources/` (the backend's config and Sokoban levels), `assets/seamcarver/output/` (seam carver results), and the backend's logs (`callTrace.log`, `server.log`). `server-deploy` never deletes them, nor anything outside the home directory, and refuses a bundle that ships any of them or would write outside the home directory, with the server's symlinks resolved. It also refuses a bundle without `server-deploy` and `server-restart`, which deploys need. Anything else no manifest lists is left alone too, such as files earlier deploys left behind before deploys kept a manifest; those are deleted by hand.

`./ship` needs `server-deploy` on the server, which every deploy updates. To put it there the first time, run once from the repository root:

```
ssh ec2-user@zyoussef.com 'cat > server-deploy && chmod 755 server-deploy' < server-deploy
```

The first deploy after that keeps a manifest and deletes nothing; later ones delete by it.

On the server, [Caddy](https://caddyserver.com) serves the site over https on ports 80 and 443, with a Let's Encrypt certificate it obtains and renews itself, and forwards requests to the Ktor server on `127.0.0.1:8080`. Its config is `Caddyfile`, which `server-restart` installs on every deploy. Caddy is set up once per server with:

```
ssh ec2-user@zyoussef.com 'bash -s' < server-setup-caddy
```

### Continuous deployment

CI's `deploy` job calls `.github/workflows/deploy.yml` once every commit CI checked for a push has passed its tests, for the push's tip. That is every commit the push brings, unless it brings more than 20: then only the newest 20 were tested.

- **Bundle** checks out the tip, sets up the build as the test jobs do, runs `./bundle --skip-tests` (the backend's tests just passed in the test job) and uploads the zip and its `MANIFEST` as the `site-bundle-<sha>` artifact (kept 7 days). It is the only job that runs the commit's code, npm and Gradle, with a read-only token.
- **Check master's tip**, on `master` only, ends the deploy there if `master` has moved on since the push: CI runs on `master` in parallel, so an older one can finish last, and the newer commit's run deploys. It runs before Ship joins the deploy queue, where a stale run would otherwise replace the newer one waiting.
- **Ship**, on `master` only, runs in the `production` environment, which only `master` may deploy from and which holds the deploy key (`SSH_KEY`) and the server's pinned host key (`KNOWN_HOSTS`). Deploys run one at a time and none is cancelled halfway (concurrency group `production`): a newer one waits, and if several wait only the newest is kept. Once it holds the queue it checks the tip again, for a commit pushed in the meantime, then sends the bundle to `server-deploy` as `./ship` does; the server limits that key to `restrict,command="~/server-deploy"`, so it can't run anything else. It keeps the manifest it shipped as the `deployed-manifest` artifact (kept 90 days), then checks the live site for about two minutes: the index must name the bundle's `assets/index-*.js`, `/graphql` must answer `{ levels }` with data (it answers errors with 200 too, and has no `__typename`) and `/assets/ppu/smb3/smb3.zgal.html` must answer 200. The site answers `HEAD` with 404, so the checks use `GET`.
- **Dry run**, on any other branch, lists the bundle, checks that its `MANIFEST` lists exactly its files, and compares the manifest with the newest `deployed-manifest` from a `master` run: the files a deploy would add and delete, also in the run's summary. Without one (before CI's first deploy, or 90 days after the last), compare the bundle's `MANIFEST` with the server's `~/.deploy/MANIFEST` by hand.

A deploy that fails leaves the run red, and a broken upload leaves the site as it was (see above). To redeploy, rerun the `Deploy / Ship` job (within the bundle artifact's 7 days), or run CI on `master` by hand (`gh workflow run ci.yml --ref master`). Run CI on `master` by hand the same way in the one case where `master`'s tip isn't deployed: a stale run that passed the tip check joins the queue in the seconds before a newer push's run does, replaces it there, and then sees the newer tip and ships nothing. (Rerunning that stale run's `Ship` skips again; rerun the tip's run or use `gh workflow run`.) When CI can't deploy, `./deploy` still does, from a checkout of `master` and with a normal login to the server; it doesn't update `deployed-manifest`, so the next dry run's comparison is with CI's last deploy.

The one-time setup, done by hand: the `production` environment with a deployment branch policy for `master` only; an ed25519 key whose public half is in the server's `~/.ssh/authorized_keys` as `restrict,command="~/server-deploy" ssh-ed25519 ... deploy@github-actions` and whose private half is the environment secret `SSH_KEY`; and `KNOWN_HOSTS`, the output of `ssh-keyscan -t ed25519 zyoussef.com` once its fingerprint is checked against a trusted connection's.
