# Zoey's Personal Site

## Testing

```
# Backend unit and API tests
cd graphql-server && ./gradlew test

# Seam carver goldens: the original Java must reproduce testdata/seamcarver
graphql-server/gradlew -p seamcarver-web check

# Seam carver Rust engine: must reproduce the goldens too, natively and as WebAssembly under Node
cd seamcarver-web/flat && cargo test && ./build.sh target/web && node node-check.mjs target/web

# Seam carver web engines: builds the Java with TeaVM and checks it against the goldens under Node
./build-seamcarver

# Frontend component tests
cd frontend && npm test

# End-to-end tests: starts the backend and a production build of the frontend
cd e2e && npm install && npx playwright install chromium firefox && npm test
```

The end-to-end tests need the git-ignored builds of the PPU's games, ZGAL's examples, the splat viewer and the seam carver's web engines first (`./build-ppu`, `./build-zgal`, `./build-splat`, which also fills `e2e/fixtures/splat`, and `./build-seamcarver`); they refuse to start without them, since about 56 ppu, splat and zgal specs would otherwise fail in ways that look unrelated. To run one spec, name its file (`npx playwright test tests/seamCarver.spec.ts`): Playwright matches a filter against the whole path, ignoring case, so `seamCarver` alone matches every spec in a checkout whose path contains "seamcarver".

`frontend/README.md` notes the traps of the component tests (jsdom's missing object URLs, module-level state shared between tests).

The end-to-end tests run in two Playwright projects, headless Chromium and headless Firefox (`npm test -- --project=firefox` runs one). Every test runs in Chromium. Firefox runs only the tests tagged `@firefox` (`test(title, { tag: '@firefox' }, ...)`, picked by the project's `grep`), so time goes to what can differ between the two browsers. Tag a test when it exercises behaviour Firefox implements differently: layout and CSS across widths, color schemes and fonts, keyboard, focus and pointer input, file inputs and uploads, or a page's fallback in a browser without WebGPU (`navigator.gpu` deleted). Leave it untagged when it only calls the backend (`{ request }`), checks only the app's own logic (such as a stubbed missing adapter, `withoutWebGPUAdapter` in `e2e/tests/pageChecks.ts`), or lists projects and links. A command-line `--grep` combines with the tag (both must match), so `--project=firefox --grep <title>` finds only tagged tests. The specs that draw with WebGPU or WebGL live in `e2e/tests/gpu/` and stay untagged: they run on Chromium's SwiftShader (see `e2e/tests/gpu/webgpu.ts`), as headless Firefox has no WebGPU adapter (on Linux it has no `navigator.gpu` at all, on macOS it has one that gives no adapter). A new spec goes in `e2e/tests/gpu/` only if it needs a GPU to draw; tests of what a page does without WebGPU, or without an adapter, stay outside it. A test that needs the page to behave as it does where WebGPU exists, such as showing a frame in place of a screenshot, applies `withoutWebGPUAdapter` too, as Firefox's own WebGPU differs by platform.

The Vulkan Retro PPU's page (`/projects/vkPPU`) runs its games in the browser on WebGPU. They are built from the [vk_ppu](https://github.com/zach-youssef/vk_ppu) submodule (`external/vk_ppu`, with its own `vulkan_test` submodule) by `./build-ppu` into `graphql-server/assets/ppu`, which git ignores and the backend serves as `/assets/ppu/<game>/`. Run it before the end-to-end tests or a local backend, and again after updating the submodule; `./bundle` (and so `./deploy`) runs it itself. Building needs what the PPU's `make web` needs: Racket 8 and Node 24 with npm.

ZGAL's page (`/projects/zgal`) likewise runs one of its examples beside the program's source, chosen with a selector that records it in the URL (`?sample=particles`, `?sample=scene` or `?sample=image_filter`; a missing or unknown value shows particles), so a link can open the page on any of them; choosing the running example again restarts it (scene stops on Esc). The examples are listed in `frontend/src/features/zgal/samples.ts`. `./build-zgal` builds ZGAL's examples that run in a browser (particles, scene and image_filter) from the [vulkan_testing](https://github.com/zach-youssef/vulkan_testing) submodule (`external/zgal`) into `graphql-server/assets/zgal`, each served as `/assets/zgal/<name>/`: its page and scripts, the runtime, whatever it loads (scene's `assets/scene.gltf` and `scene.bin`, and any `*.wasm`, which the backend serves as `application/wasm`, as `WebAssembly.instantiateStreaming` requires), the runtime's image decoder (`zgal/stb_image.wasm`, stb_image built to WebAssembly, which decodes every image a program loads or is given; `./build-zgal` fails without it), its source (`<name>.zgal`, which the backend serves as UTF-8 text so that a browser shows it) and what browsers without WebGPU see instead. For particles and scene that is a screenshot (`screenshot.webp`), the last frame of a headless run under Node on the GPU (particles at 1024x640, scene at 1280x720, 240 frames each), compressed with `cwebp` (`brew install webp`); a program is added with a `copy_program` line in `./build-zgal`, and a `screenshot` line if it has a window. Building needs what ZGAL's `make web` needs: Racket 8, Node 24 with npm, and `curl`, with which ZGAL's make downloads the wasi-sdk release it pins (clang for WebAssembly, which builds the image decoder) into `external/zgal/.cache/` the first time (`WASI_SDK_PATH` names an installed one instead). naga, which ZGAL's make builds with `cargo` (from rustup), and `glslc` (the Vulkan SDK's, or `brew install shaderc`) are needed only for programs with GLSL bodies or `extern-glsl` functions, which none of the three has. image_filter has no window: its default input, the example's 128x128 test image, is `assets/input.png` (where the program's paths resolve, so its page runs it with `?arg=input.png&arg=out.png&blur=2&edges`), and the build filters it under Node on the GPU with `--blur 2 --edges` (the example's own `blur_edges` test) into `blur_edges.png`, kept lossless as the reference a browser's run is compared with; `input.webp` and `blur_edges.webp` (quality 80) are the two to show. The page runs image_filter with its own controls rather than the program's page (`ImageFilterDemo.tsx`): it imports the main and calls its `runHeadless` with the command line the controls make (a picture, `--blur` with a radius of 1 to 64, `--edges`, and `--threshold` with a level of 0 to 1, each behind a switch), starting at the build's `input.png --blur 2 --edges`. The threshold's level starts at 0.15 rather than the program's 0.5, which turns the example's edges all black; at 0.15 about a tenth of them stay white. A picture the visitor chooses, of the types the runtime's decoder reads (the picker offers PNG, JPEG, BMP, GIF, TGA, PSD, PIC and PGM/PPM files), is given to the run as a file, and the page shows the input beside the PNG the run captures, with a link to download it. A changed control stops the last run and, once it has stopped, starts another (each has its own WebGPU device); a slider's changes wait 300 ms after the last one, so dragging it doesn't start a run at every step. Without WebGPU, or when a run of the default input fails, it shows `input.webp` and `blur_edges.webp` with an alert; a chosen picture that fails shows the program's message instead. `zgalWebGPU.spec.ts` compares its first capture with `blur_edges.png` and checks that the switches and sliders are exactly the program's non-positional options (its main's `program.options`), in their ranges, and that a JPEG the visitor chooses (the example picture, encoded by the browser) comes out as the build's output, but for what JPEG's compression changed. It also builds ZGAL's Scribble documentation into `graphql-server/assets/zgal/docs`, which the backend serves at `/zgal/docs/` (and redirects `/zgal/docs` there, since the page links its stylesheets relative to itself); the ZGAL page links to it. Last, it writes `graphql-server/assets/zgal/source.json`, served as `/assets/zgal/source.json`, which says where the copied sources come from: `{"repository": "https://github.com/zach-youssef/vulkan_testing", "commit": <the checkout's HEAD>, "dirty": <bool>}`. `dirty` is true when GitHub may not have those sources at that commit: when the checkout has changes (untracked files included), isn't the `external/zgal` submodule, isn't at the commit the site pins it to, or is at a commit none of its remote branches has (unpushed, or not fetched since). The page loads it once and links each listing to its source on GitHub at that commit (`<repository>/blob/<commit>/examples/<name>/<name>.zgal`, labelled with the short sha), or says "local build" instead when `dirty` is true. The listing always shows the copied file, so the page fetches nothing from GitHub, and it still shows, without the link, when `source.json` can't be loaded. The listing is syntax highlighted by the site's own ZGAL tokenizer (`highlightZgal.ts`, no library), which marks comments, strings, numbers (`1/60` too), booleans, `#:keywords`, brackets, `.field` accesses and the head symbol after `(` or `[`, so it needs no list of ZGAL's forms; the coloured tokens are spans with classes, never HTML, so the listing's text is the source exactly. Their colours are the themes' `$code-*` variables, each at least WCAG AA (4.5:1) on `$surface`. Its unit tests rebuild every example in `external/zgal/examples` exactly from its tokens. The checkout must be a git repository of its own; `./build-zgal` refuses anything else before building. The end-to-end tests (`zgalSource.spec.ts`) check that each served `<name>.zgal` is the one at the submodule's pinned commit, that `commit` is that commit and that `dirty` is false, and that the page lists each program exactly as it is at that commit and links it to GitHub at that commit, so a build from a changed or other checkout fails them. Both pages run their programs in frames of the programs' own pages (`ZgalFrame.tsx`); `ZgalCanvas.tsx` runs one in a canvas of the site's page instead, importing its main (`<name>.zgal.main.js`) at run time and calling its `mount` (ZGAL's "Other pages embed programs"). It stops the program on unmount and mounts it again when its main, scaling or command line changes. Every mount, in whichever `ZgalCanvas`, first waits until the programs stopped before it have stopped, as each has its own WebGPU device and copy of its assets, so a canvas re-keyed or reached again by navigating back doesn't hold a second copy of a scene. The runtime's stop aborts the program's asset downloads rather than awaiting them, so a stalled download doesn't hold up the next mount. Its `onState` and its box's `data-zgal` attribute give the state (`loading` as each mount starts, then `running`, `stopped` or `failed`). The dev and preview servers forward `/assets/zgal` to the backend, so such an import works in both.

The splat viewer (vk_splats' `splat_view`, which draws a 3D Gaussian splatting scene as it streams in) runs on WebGPU too, with a scene trained by [vk_splats](https://github.com/zach-youssef/vk_splats). `./build-splat` builds the viewer from the vk_splats submodule (`external/vk_splats`, with its own `vulkan_test` submodule) into `graphql-server/assets/splat`, which git ignores and the backend serves as `/assets/splat/`: the viewer's page, scripts and runtime in `viewer/` (a page imports `viewer/splat_view.zgal.main.js` and mounts it), the scene in `scene/` (`scene.stream` and its `cameras.bin`), `screenshot.webp` for browsers without WebGPU, and `scene.json`, which tells a page what it needs so that it hard-codes none of it: the viewer's main, the screenshot, the scene's files with their paths, sizes and sha256s, their total `bytes` (a progress bar's total, whatever the response's headers say), the splat count, SH degree and stream format version, the viewer's `size`, its command line (`args`, with root-absolute paths, which ZGAL's `mount` resolves against the page's origin), the release (`tag` and `url`) and `source`, the viewer's repository and commit with a `dirty` flag decided as `./build-zgal` decides it for its `source.json`. The scene isn't in git: it is a release's assets on vk_splats, which the tracked lock `splat-scene.json` names with their sizes and sha256s, along with the stream format version, the splat count and SH degree, and the view the page opens on (`camera` of `cameras.bin`, the canvas `size`, and `streamWords`, the 4-byte words the viewer reads a frame: 262,144, 1 MiB, given explicitly as splat_view's default is 4 MiB). `./build-splat` downloads each locked file once into `${SPLAT_CACHE_DIR}/<sha256>` (by default `${XDG_CACHE_HOME:-~/.cache}/personal-site/splat`), checks its size and sha256 before it enters the cache and every time after, and refuses a stream whose header (magic, format version, splats, SH degree) isn't the lock's, or a vk_splats checkout whose stream format version (`lib/splat_stream.zgal`) isn't the lock's, since a viewer refuses a stream of another version. It also puts the lock's fixture, a 2,000-splat stream and its cameras for the end-to-end tests, in `e2e/fixtures/splat/` (ignored by git, not shipped). The screenshot is the last frame of a headless run under Node on the GPU with the page's command line, at the lock's camera and size, but for `--stream-words`, which is splat_view's most so that a slow GPU (lavapipe in CI) loads the scene in fewer, longer frames; the run must report the whole scene loaded: it runs 32 frames, enough on lavapipe (which has the scene in 3, as Node reads the file at its own pace, and spends about 0.3 s on every frame after), and again with 480 if that wasn't enough (an M4 takes about 280); then `cwebp` compresses it (quality 80). Building needs what vk_splats' web build needs (Racket 8 and Node 24 with npm), `jq` and `curl`. The splat page (`/projects/splats`, `frontend/src/features/splat/`) loads `scene.json` and mounts the viewer in a `ZgalCanvas` with its `args`: as the page opens on a desktop, but on a touch device (a coarse primary pointer) only once the visitor presses "View in 3D (N MB)" over the screenshot, so a phone downloads the scene only when asked. A progress bar in the theme's primary colour counts the bytes the viewer's `onProgress` reports against `scene.json`'s `bytes`, from the first report until every byte has arrived (a viewer built without `onProgress` shows none). Without WebGPU, or when the viewer fails, the page shows the screenshot with an alert; once Esc has stopped the viewer, which also ends its download, a button restarts it. The dev and preview servers forward `/assets/splat` to the backend, as they do `/assets/zgal`. Run `./build-splat` before the end-to-end tests, which refuse to start without `assets/splat` and the fixture. `splat.spec.ts` checks the page without a WebGPU adapter (the controls, the screenshot with its alerts, the touch poster, and that none of them downloads the scene); `splatWebGPU.spec.ts` runs the viewer on SwiftShader with the fixture, streamed at a set pace by a local server that sees whether the browser stops reading: the progress bar, the drawn canvas, W moving the view, the failure alert for a stream that isn't a scene, and that leaving the page, routing away from it or stopping the viewer with Esc mid-stream ends the download. It also checks that the viewer accepts the real scene's header and starts streaming it, which is too large for SwiftShader to draw in time.

To swap the scene: publish the new scene as a new release on vk_splats (a new tag rather than new assets on the old one, so older commits' locks still download what they name), then in one commit update `splat-scene.json` (the tag, each file's bytes and sha256, the splat count, SH degree, stream format version and the start view) and, if the scene needs a newer viewer (a new stream format version, say), bump `external/vk_splats` with it. `./build-splat` refuses a lock whose version the pinned viewer doesn't read, so the two can't drift apart.

### Seam carver goldens

The seam carver's engines (the server's, and the browser's: the Java built by TeaVM and the Rust engine, below) must give exactly what the original Java gives. `testdata/seamcarver/` holds that oracle: for each fixture an input (`<case>.in`) and the result of the SeamCarving submodule (`graphql-server/src/java/SeamCarving`), compiled untouched, carving it to the case's target (`<case>.out`). Its `README.md` gives the file format (little-endian int32 width and height, then `0x00RRGGBB` int32 pixels, rows top to bottom) and the cases, which include the end-to-end tests' 60x40 `gradientPng`. The Gradle project `seamcarver-web/` (built with the backend's wrapper, `graphql-server/gradlew -p seamcarver-web`, on a JDK 21 toolchain) compiles the submodule into its `oracle` source set beside `GoldenWriter.java`, which draws the fixtures in memory and encodes them. Its `check` carves every case again, both from the in-memory image and from a PNG file that ImageIO decodes (the server's path), and fails on any pixel that differs from the committed golden, naming the first ones. When the Java changes on purpose, or a case is added to `GoldenWriter.CASES`, regenerate the goldens with `graphql-server/gradlew -p seamcarver-web check -Pgoldens.write=true` (or the `writeGoldens` task alone) and commit them with the change; never edit them by hand.

### Seam carver Rust engine

`seamcarver-web/flat/` is the browser's engine for large images: the Java's algorithm on flat arrays in Rust, built to WebAssembly, pixel-identical to the Java. Its `src/lib.rs` documents what the Java computes and where the engine does the same (the brightness and energy sums in the Java's order, `Math.pow(x, 2)` being `x * x`, the strict-`<` first-minimum tie-breaks, the seam's end as the leftmost or topmost minimum, horizontal seams as the vertical algorithm on the transposed image, which changes no value), and caches energies, recomputing only the pixels whose neighbourhood a removed seam changed. The exported `Carver` (`new(rgb, width, height)`, `step_vertical()`, `step_horizontal()`, `width()`, `height()`, `rgb()`, `energy_map()`, `next_vertical_seam()`, `next_horizontal_seam()`) has the stepwise shape of the TeaVM build's `WebCarver`, so one worker loop can drive both engines; a step on an image one pixel wide or high throws, and `carve` (Rust only) refuses a target outside `1..=size`. Pixels are `0x00RRGGBB` `u32`s, the top byte ignored. The toolchain is pinned in `rust-toolchain.toml` (rustup installs it on first use); `wasm-bindgen` is pinned exactly in `Cargo.toml`, and `wasm-bindgen-cli` must be that version: `cargo install --locked wasm-bindgen-cli --version "$(./build.sh wasm-bindgen-version)"`. `cargo test` runs the engine over every golden in `testdata/seamcarver` natively (and checks the edges the goldens don't reach: the energy cache against a full recomputation after every step, the announced seam being the removed one, layout changes, invalid targets, 1x1); `SEAMCARVER_GOLDENS=<dir>` runs the two "every golden" tests over another set in the same format, such as random cases written by the oracle. `./build.sh <dir>` builds the release module and its ES-module glue (`flat.js`, `flat_bg.wasm`, about 39 KB), and `node node-check.mjs <dir>` runs it under Node over every golden (`--bench` times a 1 MP and a 12 MP carve to 75% width, as `cargo bench` does natively). Measured on an M-series Mac: about 3.7 ns per pixel-seam natively and 4.8 ns under Node, so a 12 MP image losing 25% of its width takes about 50 s; the page's slow warning scales that constant by the image's pixels and the seams to remove. `./build-seamcarver` (below) builds the module the site ships into `graphql-server/assets/seamcarver-web/flat/` and its golden check covers it; `node-check.mjs` is for working on the crate alone and for the benchmark.

### Seam carver in the browser

`./build-seamcarver` builds the seam carver's engines for the browser into `graphql-server/assets/seamcarver-web`, which git ignores and the backend serves as `/assets/seamcarver-web/`: the original SeamCarving Java, built by [TeaVM](https://teavm.org) 0.17 both to WebAssembly (`java/carver.<hash>.wasm`, with its loader `java/carver.wasm-runtime.<hash>.js`, an ES module whose `load(url)` instantiates it; it needs WasmGC and the exception-handling proposal's `exnref`: Chrome 137, Firefox 131, Safari 18.4) and to JavaScript (`java/carver.<hash>.js`, an ES module, for the browsers without those); the Rust engine built to WebAssembly by `seamcarver-web/flat/build.sh` (`flat/flat.<hash>.js`, wasm-bindgen's ES-module glue, whose default export `init` takes the module's URL and whose `Carver` is the engine, and `flat/flat_bg.<hash>.wasm`); and `manifest.json`, which names those files by engine and part (`java.wasm`, `java.wasmRuntime`, `java.js`, `flat.js`, `flat.wasm`). `<hash>` is the first 16 hex digits of the file's sha256, so a name changes with its content: a copy a browser cached under a name is always the right one, a fresh manifest never names a file the browser holds stale, and a deploy can't pair old JavaScript with new WebAssembly (a page that read the manifest before the deploy can at worst get a 404 for a file it named). The backend serves JSON `no-cache` (`cachingOptions` in `Application.kt`), as it does pages, so every visit reads the manifest afresh while the files it names may be cached for a day. Both loaders take the URLs to load explicitly, so no built file names another by its path. The Java is the submodule, untouched: the Gradle project `seamcarver-web/` (the goldens' project; `graphql-server/gradlew -p seamcarver-web buildWasmGC generateJavaScript` is what the script runs) copies its sources into `build/generated/seamcarving/` as the `main` source set, leaving out the three classes built on `BufferedImage`, `ImageIO` and `File` (`FromFileImage`, `ComputedPixelImage`, `WorldImage`), which `src/main/java/SeamCarving/` replaces with versions over an `int[]` of `0xRRGGBB` pixels, and rewriting the one `import java.awt.*;` (`Pixel.java`) to `import shim.awt.*;`, where `src/main/java/shim/awt/Color.java` stands in for `java.awt.Color` (TeaVM's class library has no AWT). The copy task (`transformSeamCarving`) fails the build if the submodule changes under it: a boundary class gone, a copied file still mentioning `java.awt`, `javax.` or `java.io.File`, or the import found in any file but `Pixel.java` once. `WebCarver.java` is what the page calls (TeaVM's `@JSExport`; the module's named exports in the JavaScript build, the instance's `exports` in the WebAssembly one): `begin(rgb, width, height)`, `stepVertical()`, `stepHorizontal()`, `width()`, `height()`, `result()` (`0x00RRGGBB` pixels, the goldens' format) and `end()`, one seam at a time through the same package-private `GraphImage` methods as `SeamCarver.carve`, in its order (every vertical seam, then every horizontal one), so a worker can report progress and be stopped; the Rust engine exports the same shape. Before the script puts anything in place, `seamcarver-web/golden-check.mjs` runs all three engines over every golden in `testdata/seamcarver` under Node (`node --experimental-wasm-exnref golden-check.mjs <dir>`: Node 24 keeps `exnref` behind that flag; the script passes it only when Node accepts it) and checks that each file the manifest names is named by its content's hash; a differing pixel fails the build. Building needs Java (the wrapper picks a JDK 21 toolchain and fetches TeaVM from Maven Central), Node 24, `jq`, and the Rust toolchain and `wasm-bindgen-cli` of "Seam carver Rust engine" above; the first build takes a minute or two, later ones seconds. The Java's outputs are about 61 KB of WebAssembly, 18 KB of loader and 30 KB of JavaScript, the Rust engine's about 39 KB of WebAssembly and 10 KB of glue; the Java keeps its object graph of about 3.4 KB per pixel, so it is for small images (the page's router sends large ones to the Rust engine). The dev and preview servers forward `/assets/seamcarver-web` to the backend, as they do `/assets/zgal`, and `./bundle` runs the script and ships the directory. The end-to-end tests refuse to start without the build, and `seamCarverEngines.spec.ts` loads each build from the served assets in a bare page, in Chromium and in Firefox, and carves the `medium` golden exactly as the JVM did, so the real browsers' WebAssembly is checked on every commit, not only Node's.

## Site copy

The project cards' copy lives in `graphql-server/resources/content/projects.yaml`, one entry per project keyed by its id: `title` (the card's heading), `description` (its one-line summary) and `thumbnail` (its image, a root-relative URL such as `/assets/projectThumbnail/zgal.webp`). The projects themselves are the `ProjectId` enum (`graphql-server/src/Models/ProjectInfo/ProjectId.kt`): a constant's name is the project's public id (its URL, its GraphQL `id` and its key in the YAML), and its declaration order, category and `featured` flag set where and in which order the site lists it. Adding a project means a constant there and an entry in the YAML. The backend reads the file from its classpath at startup and refuses to start if it is malformed, misses a project, has a key that isn't a project, repeats a key or field, has a field it doesn't know, or misses a field or leaves one blank; `ProjectCopyLoaderTest` covers each case and `SimpleProjectInfoRepositoryTest` holds the expected copy, so a copy edit updates that test too.

The professional projects (category `PROFESSIONAL`), and the others listed in `ProjectWriteupLoader.WRITTEN_UP`, have a page of their own, whose copy is a write-up in `graphql-server/resources/content/writeups/<id>.yaml`, one file per project, served by the `projectWriteup(id)` query. The page's title is the card's, and so is its image unless the write-up has a video, so they aren't repeated. A write-up has `context` (one line under the title: employer, year, role), either `imageAlt` (the card image's alt text) or `video` (shown in place of the image: `youtubeId`, the 11-character id in the video's URL, and `title`), `sections` (the body, in order: each a `text`, an optional `heading`, which is left out, not left empty, and optional `figures`), and the optional `links` and `articles`. Paste a section's text into its `|` block scalar, indented: blank lines separate paragraphs, and the line breaks and indentation inside a paragraph are joined into single spaces, so hard-wrapped text is fine. A figure, shown after its section's paragraphs, has `src` (an SVG in `graphql-server/assets/writeups/<id>/`, as the root-relative URL `/assets/writeups/<id>/<name>.svg`), `alt` (what it shows, for screen readers) and `caption`; the page draws the SVG inline, so it takes the theme and its text can be selected (see "Write-up diagrams" below). A link (a button under the body, such as the project's repository) has `title` and `url` (`https://` only). To add an article, add an entry to `articles` with `title`, `source` (the publisher), `url` (`https://` only), `note` (one line on what it covers) and, if known, `date` (`"YYYY-MM"` or `"YYYY-MM-DD"`, a real month and day). The video's poster is drawn by the page, and the player is loaded from `youtube-nocookie.com` only once it's clicked. Quote dates, numbers and words like `yes`, `no`, `on` and `off`: YAML would read them as something other than text, and the backend refuses them unquoted (in `projects.yaml` too). Placeholder copy starts with `TODO(copy)`, so it can be found with grep. The backend loads a file for each of those projects and refuses to start if one is missing or invalid (the rules above, plus a blank field, an empty list or list item, an empty `heading:`, a URL that isn't `https://`, a date that isn't real, a note with a line break, a malformed YouTube id or a figure `src` outside `/assets/writeups/`); `ProjectWriteupLoaderTest` covers each case and fails if the directory holds a file for any other project, and `ProjectWriteupRepositoryTest` checks the site's write-ups, including that each figure's file exists.

### Write-up diagrams

A write-up's figures are hand-written SVGs in `graphql-server/assets/writeups/<id>/`, which the page fetches and puts in the document itself (`WriteupFigure`), rather than showing them with `<img>`, so that the site's stylesheet colours them for the current theme and their text stays selectable. They give their shapes and text these classes, which `.writeup-figure` in `frontend/src/theme/_overrides.scss` colours from the theme's palette: `wd-text` (body text), `wd-muted` (labels and column headings), `wd-mono` (monospaced, for keys and values), `wd-node` (a plain box), `wd-db` (the database), `wd-file` and `wd-dir` (a file's and a directory's keys), `wd-value` (a value), `wd-arrow` (a line) and `wd-arrowhead` (its head, a filled shape rather than a `<marker>`, whose id would clash between diagrams on one page). Each element also carries the light theme's colours as `fill` and `stroke` attributes, which the classes override on the site, so the file still reads when opened alone. Give the `<svg>` a `viewBox` and no `width` or `height` (the page removes them and scales it to the column; under 30rem wide it scrolls sideways instead), text sizes in its units, and no scripts, event handlers or `<foreignObject>` (the page removes them). The page names the diagram to screen readers with the figure's `alt` and drops the file's `<title>`.

### Content-Security-Policy

The site's only Content-Security-Policy is `frame-src 'self' https://www.youtube-nocookie.com`, a `<meta>` tag in `frontend/index.html`, so it applies wherever the page is served (Ktor, the Vite preview server in the end-to-end tests, the dev server) and needs no server header. Frames may show only the site's own pages (ZGAL's demos) and YouTube's privacy-enhanced player, which a write-up's video loads once it's clicked; nothing else is restricted. A new embed from another origin needs its origin added there; the end-to-end test "frames may come only from the site and youtube-nocookie.com" checks the policy.

## CI

GitHub Actions (`.github/workflows/ci.yml`) builds and tests every commit a push brings, each in its own job on `ubuntu-24.04`: on `master` the commits the push added, on any other branch every commit that `master` doesn't have; in either case the newest 20 at most. A newer push to a working branch cancels the checks still running for its older one, while every push to `master` is checked in full. Each job runs `tests/deploy-test.sh` (with its lock tests, as the runner has `flock`), the frontend tests, `./build-ppu`, `./build-zgal`, `./build-splat`, the backend tests, the seam carver goldens, the seam carver Rust engine (`cargo fmt --check`, `cargo clippy`, `cargo test`; see "Testing"), `./build-seamcarver` (the TeaVM builds and the Rust engine's WebAssembly, checked against the goldens under Node) and the end-to-end tests, and its commit gets a `CI / test` commit status, so a branch shows which of its commits pass.

- The public submodules are checked out over https. SeamCarving is private, so it's checked out with a read-only deploy key on [SeamCarving](https://github.com/zach-youssef/SeamCarving), whose private half is the repository secret `SEAMCARVING_DEPLOY_KEY`.
- Without a GPU, `./build-zgal` and `./build-splat` draw their screenshots on Mesa's software Vulkan driver (lavapipe), so they can differ from those drawn on a Mac. Each job uploads them as the `screenshots-<sha>` artifact (`zgal/<name>/screenshot.webp`, `zgal/image_filter/blur_edges.png` and `splat/screenshot.webp`).
- `./build-splat`'s downloads of the locked scene are cached (`actions/cache` on `~/.cache/personal-site/splat`, which setup-build hands `./build-splat` as `SPLAT_CACHE_DIR`) under a key made of the sha256s in `splat-scene.json`, so a job downloads the scene only when the lock names a new one; `./build-splat` checks every cached file against the lock anyway.
- The end-to-end tests run in Chromium, and the tests tagged `@firefox` in Firefox too (see "Testing"); the GPU specs (`e2e/tests/gpu/`) run in Chromium only. Those run Chromium's WebGPU on SwiftShader rather than a GPU, so CI and a Mac run them the same way (see `e2e/tests/gpu/webgpu.ts`).
- Tests print a dot each and their failures in full when `CI` is set. On a failure, the job uploads the Playwright report with the failures' traces (`e2e-report-<sha>`), the backend's test report (`backend-test-report-<sha>`) and the goldens' (`seamcarver-web-test-report-<sha>`); `gh run download <run id>` fetches them.

Notes for editing the workflow:

- The submodule checkouts, the splat scene's download cache, the wasi-sdk that ZGAL's make downloads into `external/zgal/.cache/` (cached by the version ZGAL pins, so it downloads only when that changes), the Rust toolchain that `seamcarver-web/flat/rust-toolchain.toml` pins (`rustup toolchain install` there) with `wasm-bindgen-cli` (compiled by `cargo install`, so the binary is cached by its version, which `build.sh wasm-bindgen-version` reads from `Cargo.lock`; the deploy workflow's bundle job gets both too, for `./build-seamcarver`, which costs it one 3-minute compile per version on `master`, since a branch's cache isn't visible there) and the toolchains (Racket, Node, Java, Gradle, lavapipe, cwebp) are set up by the local action `.github/actions/setup-build`, which every job that builds the site uses. A job must check out the repository before it can use it. The test jobs run the steps of the pushed tip's `ci.yml`, but each uses the setup-build of the commit it checks out, so a commit that a new step needs set up must set it up itself (e.g. the vk_splats checkout comes with the submodule, before `./build-splat`'s CI step).
- `actionlint` (`brew install actionlint shellcheck`) checks the workflows and their scripts locally; its only expected findings are the unused `try` loop variables.
- Status functions (`cancelled()`, `failure()`) are only allowed in `if:`. In `env:` they make the whole workflow fail to parse, as a 0 s "workflow file issue" run with no message; use `job.status` there.
- `git -c url.<https>.insteadOf=<ssh> submodule update --recursive` passes the rewrite on to nested submodules (through `GIT_CONFIG_PARAMETERS`), so it needs no global rewrite, which would also send the private SeamCarving over https.
- Every third-party action is pinned to a full commit sha with its release in a comment (`# v7.0.1`), as a tag can be moved to other code, and the deploy job holds the server's SSH credentials. To update one, resolve the new tag's commit (`gh api repos/<owner>/<repo>/git/ref/tags/<tag>`, dereferencing an annotated tag) and change the sha and the comment together.
- `gradle/actions/setup-gradle` stays on v5, the last MIT major: v6 accepts the Terms of Use of a closed-source caching component.
- The SeamCarving checkout (in `setup-build`), which holds the deploy key, runs before any npm, Gradle or build step, so no third-party script runs before the key is used and removed.
- Only jobs that run no code from the commits, npm, Gradle or third-party actions hold a token that can post statuses, as a job's steps share one user and file system (a build could plant a `gh` that a later step runs with the token). The test jobs get `contents: read` and no `GH_TOKEN`, and no checkout persists its credentials. The `pending` job marks every commit pending; the `statuses` job, which needs those and the test jobs, posts each commit's status from the conclusion of its job (named `Test <sha>`) in the run's jobs API, linked to that job: anything but success or failure (cancelled, timed out, skipped or unreadable) is an `error`, so none stays pending. Neither of the two checks anything out.

## Dependency updates

Dependabot (`.github/dependabot.yml`) opens weekly (Monday) version-update PRs: one grouped PR per ecosystem for minor and patch updates (npm in `frontend/` and `e2e/`, Gradle in `graphql-server/` and `seamcarver-web/`, Cargo in `seamcarver-web/flat/`, GitHub Actions in the workflows and in `.github/actions/setup-build`), and a separate PR for each major update. A Cargo PR that bumps `wasm-bindgen` carries `wasm-bindgen-cli` with it, since CI installs the version `Cargo.lock` names; the Rust toolchain pin (`rust-toolchain.toml`) isn't Dependabot's and is bumped by hand. Merging to `master` deploys through CD, so each merge is a deliberate decision: read the PR and let CI pass first. Dependabot security updates are on too (a repository setting, not in the file). Submodule pins aren't managed by Dependabot; they're bumped by hand.

- Dependabot's Gradle support reads literal versions in `build.gradle.kts` (the Kotlin plugin, which also sets kotlin-stdlib and kotlin-reflect, and `jackson-bom`). Whether it follows the `$ktor_version`-style variables in `gradle.properties` (Ktor, Logback and KGraphQL) isn't guaranteed, so check that its PRs cover them; if one never appears, update that version by hand.
- Workflow runs that Dependabot triggers see only Dependabot secrets, not the repository's Actions secrets. CI's SeamCarving checkout needs `SEAMCARVING_DEPLOY_KEY`, so a second read-only deploy key on SeamCarving (titled `personal-site-dependabot`, revocable on its own) is stored as the Dependabot secret of the same name (`gh secret set SEAMCARVING_DEPLOY_KEY --app dependabot < key`); without it, CI on Dependabot's branches fails at the checkout. Deploy secrets (`SSH_KEY`, `KNOWN_HOSTS`) stay out of Dependabot, since only `master` ships.
- Scanners and Dependabot only see published advisories and newer releases. Review the dependencies by hand roughly every quarter for libraries that are dead or unmaintained and frameworks that are end-of-life (Ktor 1.x and Logback 1.2 are examples).

## Deployment

Pushing to `master` deploys the site, once CI passes (see "Continuous deployment" below). `./deploy` does the same from a local checkout, as a manual fallback: it builds the site and deploys it to the server. It runs the two steps a deploy has, which can also run apart (e.g. building once and shipping the result later):

```
./bundle [--skip-tests] <out-dir>   # build into <out-dir>/site-bundle.zip, with a copy of its MANIFEST
./ship <bundle.zip>                 # deploy that bundle
```

`./bundle` builds the frontend, the PPU's games, ZGAL's examples, the splat viewer with its scene, the seam carver's web engines and the backend, and zips them with `server-restart`, `server-deploy` and `Caddyfile`, laid out as they go in the server's home directory. Of `graphql-server/assets` only the files git tracks ship, besides the PPU's, ZGAL's, the splat viewer's and the seam carver's builds (`assets/splat`, about 26 MB, nearly all of it the scene's stream), so untracked local files don't. ZGAL's build includes `source.json`, and the splat viewer's `scene.json`, which record the commit their sources were copied from; check that both say `"dirty": false` before shipping a bundle built locally. The zip's `MANIFEST` lists every file in it.

`./ship` sends the zip over ssh to `server-deploy` on the server, on its stdin, as the only command it runs, so it also works with a deploy key limited to `restrict,command="~/server-deploy"` in `~/.ssh/authorized_keys`. `server-deploy` unpacks the zip into `~/.deploy/staging` and checks it before changing anything, so a broken upload leaves the site as it was. It then moves the files into place, deletes the files the previous deploy's manifest (kept in `~/.deploy/MANIFEST`) listed and this one doesn't, keeps the new manifest and runs `server-restart`. A file it can't delete is reported and the deploy carries on, failing at the end. Once the upload is in, a dropped ssh session doesn't stop it; `~/.deploy/log` holds the last deploy's messages. Deploys run one at a time under a lock taken with `flock`, which the server needs (util-linux). Renaming or removing a file needs nothing more than the change itself: the next deploy deletes the old one from the server. That includes a path changing between file and directory: an old deploy's file or directory in the way is deleted before the install, while anything else in the way refuses the bundle. `tests/deploy-test.sh` tests `server-deploy` against temporary directories.

The server also holds files that no deploy ships but that are still in use: `resources/` (the backend's config and Sokoban levels), `assets/seamcarver/output/` (seam carver results), and the backend's logs (`callTrace.log`, `server.log`). `server-deploy` never deletes them, nor anything outside the home directory, and refuses a bundle that ships any of them or would write outside the home directory, with the server's symlinks resolved. It also refuses a bundle without `server-deploy` and `server-restart`, which deploys need. Anything else no manifest lists is left alone too, such as files earlier deploys left behind before deploys kept a manifest; those are deleted by hand.

`./ship` needs `server-deploy` on the server, which every deploy updates. To put it there the first time, run once from the repository root:

```
ssh ec2-user@zyoussef.com 'cat > server-deploy && chmod 755 server-deploy' < server-deploy
```

The first deploy after that keeps a manifest and deletes nothing; later ones delete by it.

The server needs Java 21 (the `java` on its `PATH`, which `server-restart` starts the backend's jar with), as the backend is built for it (see `graphql-server/README.md`).

On the server, [Caddy](https://caddyserver.com) serves the site over https on ports 80 and 443, with a Let's Encrypt certificate it obtains and renews itself, and forwards requests to the Ktor server on `127.0.0.1:8080`. Its config is `Caddyfile`, which `server-restart` installs on every deploy. Caddy is set up once per server with:

```
ssh ec2-user@zyoussef.com 'bash -s' < server-setup-caddy
```

### Continuous deployment

CI's `deploy` job calls `.github/workflows/deploy.yml` once every commit CI checked for a push has passed its tests, for the push's tip. That is every commit the push brings, unless it brings more than 20: then only the newest 20 were tested.

- **Bundle** checks out the tip, sets up the build as the test jobs do, runs `./bundle --skip-tests` (the backend's tests just passed in the test job) and uploads the zip and its `MANIFEST` as the `site-bundle-<sha>` artifact (kept 7 days). It is the only job that runs the commit's code, npm and Gradle, with a read-only token.
- **Check master's tip**, on `master` only, ends the deploy there if `master` has moved on since the push: CI runs on `master` in parallel, so an older one can finish last, and the newer commit's run deploys. It runs before Ship joins the deploy queue, where a stale run would otherwise replace the newer one waiting.
- **Ship**, on `master` only, runs in the `production` environment, which only `master` may deploy from and which holds the deploy key (`SSH_KEY`) and the server's pinned host key (`KNOWN_HOSTS`). Deploys run one at a time and none is cancelled halfway (concurrency group `production`): a newer one waits, and if several wait only the newest is kept. Once it holds the queue it checks the tip again, for a commit pushed in the meantime, then sends the bundle to `server-deploy` as `./ship` does; the server limits that key to `restrict,command="~/server-deploy"`, so it can't run anything else. It keeps the manifest it shipped as the `deployed-manifest` artifact (kept 90 days), then checks the live site for about two minutes: the index must name the bundle's `assets/index-*.js`, `/graphql` must answer `{ levels }` with data (it answers errors with 200 too, and has no `__typename`), `/assets/ppu/smb3/smb3.zgal.html` must answer 200, `/assets/splat/scene.json` must answer a scene description, and the stream it names must start with its header's magic (`SPLS`) and the format version it gives (only the first 8 bytes are read), and `/assets/seamcarver-web/manifest.json` must name the Java's WebAssembly module, which must start with WebAssembly's magic (`\0asm`). The site answers `HEAD` with 404, so the checks use `GET`.
- **Dry run**, on any other branch, lists the bundle, checks that its `MANIFEST` lists exactly its files, and compares the manifest with the newest `deployed-manifest` from a `master` run: the files a deploy would add and delete, also in the run's summary. Without one (before CI's first deploy, or 90 days after the last), compare the bundle's `MANIFEST` with the server's `~/.deploy/MANIFEST` by hand.

A deploy that fails leaves the run red, and a broken upload leaves the site as it was (see above). To redeploy, rerun the `Deploy / Ship` job (within the bundle artifact's 7 days), or run CI on `master` by hand (`gh workflow run ci.yml --ref master`). Run CI on `master` by hand the same way in the one case where `master`'s tip isn't deployed: a stale run that passed the tip check joins the queue in the seconds before a newer push's run does, replaces it there, and then sees the newer tip and ships nothing. (Rerunning that stale run's `Ship` skips again; rerun the tip's run or use `gh workflow run`.) When CI can't deploy, `./deploy` still does, from a checkout of `master` and with a normal login to the server; it doesn't update `deployed-manifest`, so the next dry run's comparison is with CI's last deploy.

The one-time setup, done by hand: the `production` environment with a deployment branch policy for `master` only; an ed25519 key whose public half is in the server's `~/.ssh/authorized_keys` as `restrict,command="~/server-deploy" ssh-ed25519 ... deploy@github-actions` and whose private half is the environment secret `SSH_KEY`; and `KNOWN_HOSTS`, the output of `ssh-keyscan -t ed25519 zyoussef.com` once its fingerprint is checked against a trusted connection's.
